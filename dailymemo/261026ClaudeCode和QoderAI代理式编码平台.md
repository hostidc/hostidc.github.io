   两者的设计初衷都是为了简化开发流程，将 AI 深度集成到开发环境中，从而帮助开发者和工程团队自动化日常任务并更快地交付软件finance.yahoo.com

### 1. `.qoder/rules` 目录（项目级规则）

。

### 2. `AGENTS.md`（CLI 默认上下文文件）

如果你使用 Qoder CLI，它有一个默认的上下文文件名称叫做 `AGENTS.md` qoder.mintlify.app

。这个文件非常适合用来托管整体的项目指令、环境配置（如如何运行项目、端口、环境变量）以及稳定的开发约定，类似于社区中流行的 `CLAUDE.md` 或 `.cursorrules`。

### 3. Repo Wiki（结构化项目知识库）

除了手动编写规则文件，Qoder 还提供了 **Repo Wiki** 功能 docs.qoder.com

。它可以自动分析整个代码库，并生成涵盖架构、模块关系等的结构化 Markdown 文档 skywork.ai

。这些生成的 Wiki 文件会作为 AI 的“长期记忆”和上下文，帮助 Agent 更好地理解复杂的项目全貌。

### 4. `@` 引用机制（动态上下文注入）

在实际使用中，Qoder 支持灵活的上下文调用。例如，在聊天或 Agent 任务中，你可以通过 `@rule` 等命令，直接引用 `.qoder/rules` 目录下的特定 `.md` 文件，将其作为持久化上下文实时注入给 AI docs.qoder.com

。

这 50 条提问，正是 **“判断力”** 的具体体现。它们不是关于“语法怎么写”或“API怎么调”，而是关于​**为什么做、怎么做更好、以及潜在的风险是什么**​。

初级开发者与高级开发者的差距，就隐藏在对这些问题的追问深度和回答质量中。以下按照 Agentic 开发者的核心工作流，分为 5 个阶段，每个阶段 10 条苏格拉底式追问：

### 阶段一：需求澄清与边界定义（定义“应该实现什么”）

*差距体现：初级开发者直接让 Agent 翻译需求文档；高级开发者先解构需求，寻找真正的业务价值与边界。*

1. 这个需求的核心业务价值是什么，而不是它表面上要求的技术实现是什么？
2. 如果完全不做这个功能，业务会受到什么实质性影响？
3. 这个需求的“成功验收标准”中，哪些是可量化的，哪些是主观的？
4. 这个功能在极端情况（如高并发、断网、脏数据输入）下的预期行为是什么？
5. 我们是在解决一个真实存在的用户痛点，还是在为一个假设的场景过度设计？
6. 这个需求与系统现有的哪些核心原则或业务规则存在潜在冲突？
7. 如果只能保留这个需求中 20% 的功能，哪 20% 能解决 80% 的问题（MVP 思维）？
8. 这个需求的边界在哪里？哪些明确属于“本期不做（Out of Scope）”的范围？
9. 这个功能的生命周期预计是多久？它需要为未来扩展预留接口，还是应该保持极简？
10. 用户真正想要的“结果”是什么，而不是他们口头要求的“按钮”或“表单”是什么？

### 阶段二：架构设计与技术权衡（做“设计权衡”）

*差距体现：初级开发者接受 Agent 给出的第一个可行方案；高级开发者评估多个方案的 Trade-off（权衡）。*

11. 引入这个新技术/框架，我们获得了什么，又牺牲了什么（复杂度、学习成本、运维负担）？
12. 这个架构决策在 1 年后看是明智的，还是会成为沉重的技术债务？
13. 如果这个核心服务宕机，系统的降级策略是什么？数据一致性如何保证？
14. 我们是选择“快速上线验证”的简单架构，还是“长期可维护”的复杂架构，依据是什么？
15. 这个设计是否违反了单一职责原则，或导致了不必要的循环依赖？
16. 数据流向是否清晰？是否存在隐蔽的性能瓶颈或安全盲区？
17. 这个方案是行业内的最佳实践，还是仅仅因为“我们一直这么做”或“Agent 默认这么写”？
18. 如果团队规模扩大一倍，这个架构还能支撑吗？哪里会最先崩溃？
19. 我们是在解决当前的性能问题，还是在为未来 5 年可能不会发生的流量做过度优化？
20. 这个组件的可替换性如何？如果供应商锁定或开源项目停更，迁移成本有多大？

### 阶段三：上下文构建与规则制定（维护“项目上下文”）

*差距体现：初级开发者抱怨 Agent 听不懂；高级开发者反思是否提供了足够高质量的上下文和约束。*

21. 我提供给 Agent 的上下文，是否包含了足够的“业务约束”，而不仅仅是“技术语法”？
22. 在 `AGENTS.md` 或规则文件中，我是否明确定义了“绝对不要做的事情”（Negative Constraints）？
23. 这个提示词（Prompt）是否清晰地指出了输入、预期输出以及中间的推理步骤（Chain of Thought）？
24. 我是否向 Agent 解释了 *为什么* 我们要用这种设计模式，而不仅仅是 *怎么* 用？
25. 当前的项目文档是否足以让一个完全陌生的高级开发者（或 Agent）在 10 分钟内理解核心逻辑？
26. 我是否把隐性的团队约定（如命名规范、错误处理习惯）显性化地写入了规则文件？
27. 当 Agent 产生幻觉时，是我的上下文缺失了关键前提，还是模型本身的推理能力到达了瓶颈？
28. 我是否将复杂的任务拆解成了 Agent 可以独立验证的、原子化的子任务？
29. 这个上下文文件是否随着代码的演进保持了同步更新，还是已经变成了过时的误导信息？
30. 我是否在提示词中赋予了 Agent 特定的“角色”和“审查标准”，以提升其输出的专业度？

### 阶段四：代码审查与结果评估（审查与“何时推翻”）

*差距体现：初级开发者看到代码跑通就合并；高级开发者像严苛的主编一样审查每一行生成的代码。*

31. 这段 Agent 生成的代码，如果由我来手写，我会写得不同吗？为什么？
32. 这段代码在处理边界条件（如 null、空数组、超大数值、并发竞争）时是否足够健壮？
33. Agent 是否引入了不必要的第三方依赖，从而增加了供应链安全风险或包体积？
34. 这段代码的可读性如何？6 个月后的我（或同事）能一眼看懂它的意图吗？
35. Agent 的解决方案是否过度工程化了？有没有更简单、更直接的实现方式（YAGNI 原则）？
36. 这个修改是否无意中破坏了系统其他部分的隐式契约（回归测试覆盖了吗）？
37. 当 Agent 给出一个看似完美的答案时，我是否进行了独立的逻辑推演或编写了反例来验证它？
38. 这段代码的错误处理机制是静默失败、抛出明确异常，还是提供了可操作的恢复建议？
39. 我是否盲目接受了 Agent 的重构建议，而没有评估其带来的实际性能或维护性收益？
40. 如果这段代码在生产环境引发 P0 级故障，我能根据现有的日志和结构在 5 分钟内定位问题吗？

### 阶段五：系统演进与哲学反思（高级判断力）

*差距体现：初级开发者关注“任务完成”；高级开发者关注系统的长期健康、团队成长与技术的本质。*

41. 我们是在用技术解决业务问题，还是在为了使用新技术而强行寻找业务场景？
42. 这个系统的“本质复杂度”（业务本身决定的）和“偶然复杂度”（技术实现带来的）比例健康吗？
43. 如果明天所有 AI 编码助手都失效了，我们的代码库还能被人类开发者顺利接手和维护吗？
44. 我作为开发者，今天是在“思考”，还是仅仅在做 AI 的“高级打字员”和“提示词搬运工”？
45. 这个决策是否充分考虑了非功能性需求（安全性、合规性、可访问性、甚至碳排放）？
46. 我们是否在不知不觉中，将系统的核心业务逻辑耦合到了某个特定 AI 模型的偏好或能力上？
47. 当业务需求发生 180 度转变时，当前的代码结构是具备弹性，还是需要推倒重来？
48. 我是否清楚地知道，在这个特定场景下，人类直觉、伦理判断和经验仍然优于 AI 统计概率的领域在哪里？
49. 这个功能的增加，是让系统变得更简单了，还是只是把复杂度转移到了用户或运维端？
50. 最终，这个软件是否真正尊重了它的使用者，并为这个世界创造了净正向的价值？

### 💡 如何最大化这些 Spec 的威力？

1. ​**组合使用**​：不要孤立使用。例如，先用 **#10** 拆解需求，然后用 **#21** 并行生成后端代码和测试，最后用 **#42** 将其纳入 CI/CD。
2. ​**注入项目上下文**​：在每个 Prompt 的开头，加上 `@AGENTS.md` 或 `@rules/backend_rules.md`（如果你使用 Qoder），确保 Agent 在生成这些 Spec 时，严格遵守你已有的项目规范。
